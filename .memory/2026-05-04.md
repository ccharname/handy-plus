## 你早上要做的关键决策

### 决策 1：Round B 启动 / 暂缓 / 走 Swift 路径

三选一：

**A. 启动 Round B（Python sidecar）**
- 工程量 ~7-9 天，分 Phase B1（sidecar 基建 4-5 天）+ B2（Voxtral wire 3-4 天）+ B3（多引擎扩展 2-3d each）
- bundle 从当前 40 MB → ~490 MB（含 Python 解释器 + mlx-audio + 依赖），模型权重另下载 2.9 GB
- 启动前必做：`entitlements.mac.plist` 加 `cs.allow-unsigned-executable-memory`（**今晚验证缺失**，不加 MLX 必崩）

**B. 暂缓 Round B，先享 A 一段时间**
- A 已经把"流式上屏"UX 给 Apple 档拿到了，先实战看体感
- 体感够好，Round B 优先级降级
- 体感不够（比如 Apple SFSpeechRecognizer 中文识别准确率不行），再上 Round B

**C. 走 mlx-audio-swift（Phase C）**
- `Blaizzy/mlx-audio-swift` 原生 Swift SDK，无 Python sidecar
- 工程量 ~+1-2 周（vs Python 路径），但消除 bundle 膨胀 + 签名 145 dylib 复杂度
- 结构上跟现 `swift/apple_speech.swift` 同形态（@_cdecl FFI bridge）
- 长期最优，**短期最贵**

**我的建议**：先 B（暂缓）一两天看 A 实战。Apple 档跑顺再考虑 C 路径直接拿 mlx 真流式同时不引入 Python 地基。如果 A 实战发现 SFSpeechRecognizer 中文准确率太烂（这是已知风险），那时再判断 A vs C 工程量。

### 决策 2：Round B 启动时的 bundle 策略（前置约束）

如果选 A 启动 Round B，需提前定：
- **bundled**：sidecar 进 .app（490 MB bundle），用户零配置 → 推荐给 power user 受众
- **unbundled**：用户自己 `pip install mlx-audio`，bundle 保持 40 MB → 装机门槛高

### 决策 3：SpeechAnalyzer 死路怎么办

之前给 macOS 26+ 写的 SpeechAnalyzer 路径已 force-disabled（commit `7e2b8db`，崩在 `SpeechRecognizerWorker.preRunRecognition`）。修复需先 `await SpeechTranscriber.downloadModel(for: locale)` 安装本地模型，再回到 dispatch gate。
- 估时：~2-3 小时
- 优先级：低（legacy SFSpeechRecognizer 路径完全够用，新 API 性能优势不显著直到长录音场景）
