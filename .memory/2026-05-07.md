### 踩过的坑

1. **mlx-audio-swift Qwen3ASRModel API 注入点选择**
   - 上游 `STTGenerateParameters` 不暴露 context/prompt 字段
   - 但 `Qwen3ASRModel.buildPrompt` 是 `public`，且 `callAsFunction(inputIds:inputFeatures:featureAttentionMask:cache:)` 也 `public` → bridge 层重定义这两个就行，**无需 fork 上游**
   - 关键陷阱：`Qwen3ASRModel.model`（Qwen3ASRTextModel）属性是 `internal`，不能直接调 `model.embedTokens` — 必须走 `callAsFunction` 让模型内部处理 embedding + audio feature merging
   - 一般化：mlx-audio-swift 上游许多内部类型用 `internal` 见 visibility，跨模块用要么走 public methods 要么本地重定义（如 BridgeSendableBox vs 上游 UncheckedSendableBox）

2. **vad-rs v0.1.6 cjpais fork 写死 v4 LSTM schema**
   - Silero v5 改成 STFT-based 架构（3 inputs `input/state/sr` + 2 outputs `output/stateN`），不再用 LSTM
   - vad-rs::Vad::compute 硬编码 4 inputs `input/sr/h/c` + 3 outputs `hn/cn/output` → 直接换 onnx 文件 ort 会 panic "input shape mismatch"
   - 一般化：drop-in onnx swap 只在 model architecture 不变时成立；schema 变了需要 wrapper 升级或 fork

3. **lucky-daemon control server 响应慢但不死**
   - lucky-ctl cron add 命令 stdout 长时间空白 ≠ daemon hang
   - 实测 18 分钟后 daemon 仍能返回 `{"created": "..."}` JSON 响应
   - 一般化：socket-based daemon API 等响应**至少给 30 分钟**再判 hang，不要拿 stdout 空白当死亡信号
   - 触发原因可能：daemon 同时跑 long-running task (e.g. miniflux_feedback_poll) 抢占 control server async coroutine

4. **CJK 中字 filler regex `\b` 不 fire**
   - regex `(?i)\b嗯\b` 在 CJK 字符之间没有 word boundary（CJK char 之间不是 word break）
   - 修法：CJK-only 的 filler 走 `String::replace` 直接 char-substitution，绕开 regex，并 swallow 跟随的 ,。，。
   - 一般化：所有依赖 `\b` 的中文文本处理都要 audit，至少加 ASCII/CJK 边界识别

5. **tauri-plugin-log RotationStrategy::KeepOne 是隐性 retention 限制**
   - default `max_file_size: 500_000` (500KB) + KeepOne = 单天数据就被覆盖
   - 任何"未来要做 audit / 回头看"的项目必须先 audit log 配置，否则数据没了 retro 跑空
   - 一般化：lib 默认 sane 但 audit 用途下都要重审 — `max_file_size` / `KeepN` / db `LIMIT` / cleanup_old 等所有 retention 旋钮一起看

6. **lucky daemon 收到 dup id 拒绝插入，store 不会污染**
   - 我手动 patch cron-jobs.json + lucky-ctl API 双路径并行写入，最终 store 仍然只有 1 条 entry
   - 因为 daemon `_handle_add` 会 check `store.get_job(job.id)` → 已存在直接 409 Conflict 不写
   - 一般化：lucky daemon 的 cron store 写入是幂等友好的，但如果是 race condition 在两个不同 ID 上仍会双写
