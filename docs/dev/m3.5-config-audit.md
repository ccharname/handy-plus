### 1. Cargo release profile

**当前值** (`src-tauri/Cargo.toml:123-127`):
```toml
[profile.release]
lto = true
codegen-units = 1
strip = true
panic = "unwind"
```

**证据**：
- `lto = true` → thin LTO（Rust 默认，非 fat）；`codegen-units = 1` 已是最激进
- `strip = true` → 等价 `strip = "debuginfo"`，剥去调试信息但**保留符号表**，binary 未达最小
- `panic = "unwind"` → 保留 unwind tables（加载/运行时有 overhead，desktop app 实际无需）
- `opt-level` 未显式设置 → release 默认 = 3，✅ 已最优

**候选值**：
1. `strip = "symbols"` — 连符号表一并剥去，binary 再缩 15-25%；与 `strip = true` 区别：前者仅留外部符号
2. `panic = "abort"` — 删 unwind tables，binary -5-8%，startup 轻微提速
3. `lto = "fat"` — 跨 crate 全局 LTO，比 thin 更激进，binary -5-10%，但编译时间 ×3-5；当前 `lto = true` 已是 thin LTO，收益边际递减

**预期影响**：
- `strip = "symbols"`: binary -15-25%；启动 mmap 略快；无运行时影响
- `panic = "abort"`: binary -5-8%；删 unwind 逻辑，边缘热路径微提速 <1%
- `lto = "fat"`: binary 体积 -5-10%，可能有内联增益 1-3% RTF，编译时间大涨

**风险**：
- `strip = "symbols"`: macOS crash 报告无法 symbolicate（生产 app 通常可接受，开发期需留 dSYM）
- `panic = "abort"`: panic 后进程直接退出，无 Drop/catch_unwind；desktop app 通常 OK
- `lto = "fat"`: 本地开发慢 3-5×；建议仅 CI release build 用（可加 `[profile.release-dev]` 区分）

**ROI**: **高**（`panic = "abort"` + `strip = "symbols"` 是标准 desktop release 配置，零精度损失，改动 2 行）

### 2. ONNX session options (transcribe-rs SenseVoice)

**当前值**：
- `src-tauri/Cargo.toml:74`: `transcribe-rs = { version = "0.3.8", features = ["onnx"] }` — 无 `ort-coreml` feature
- `transcribe-rs-0.3.8/src/onnx/session.rs:106`: `GraphOptimizationLevel::Level3` ✅ 已最优
- `transcribe-rs-0.3.8/src/onnx/session.rs:151`: `create_session` 调用 `build_session(path, None, true)` — `intra_threads = None`（ORT 默认，通常 = 物理核数）
- `src-tauri/src/settings.rs:243-250`: `OrtAcceleratorSetting` enum 枚举值：`Auto / Cpu / Cuda / DirectMl / Rocm`——**无 CoreMl 变体**
- `transcribe-rs-0.3.8/src/onnx/session.rs:50-57`: CoreML EP 代码存在，但被 `#[cfg(feature = "ort-coreml")]` 保护

**分析**：
- `features = ["onnx"]` 未包含 `ort-coreml` → CoreML EP 在编译时被 cfg-gate 掉 → `Auto` 模式下 CoreML 不生效
- Apple Silicon M 系列芯片：CoreML EP 通常比纯 CPU 快 2-5×（for transformer/CTC models），是最大的单条遗留优化机会
- `intra_threads = None`：ORT 默认 = 物理核数，M2/M3 通常为 8-12；SenseVoice CTC decode 是顺序任务，过多线程反而增加调度 overhead；建议实测 4-6

**候选值**：
1. `transcribe-rs = { version = "0.3.8", features = ["onnx", "ort-coreml"] }` — 启用 CoreML EP（Cargo.toml 一行改动）
2. `OrtAcceleratorSetting` 加 `CoreMl` 变体 → settings.rs 约 3 行；`apply_accelerator_settings` 加一条 match arm
3. `create_session_with_threads(path, 4)` 代替 `create_session(path)` — transcription.rs 一行改动，需 before/after 测
4. 设置默认 accelerator 为 CoreMl on macOS aarch64（编译时条件）

**预期影响**：
- CoreML EP on Apple Silicon: t5_inference RTF 估 -30-60%（参考 whisper-rs + CoreML 实测数据；SenseVoice 是 CTC 模型，不是 attention，加速比可能偏保守）
- intra_threads = 4: t5_inference -5-15%（减调度 overhead），需实测

**风险**：
- CoreML EP 首次运行会编译 ML program（cold start +1-3s），后续缓存到 `~/Library/Caches/`
- CoreML EP 在部分 ONNX op 上有 fallback 到 CPU，SenseVoice CTC decode 的 op 集需要实测确认是否 100% 支持；若 fallback 多则净收益低
- intra_threads 过小（<2）反而降速，要测 2/4/6 三档

**ROI**: **高**（CoreML EP 是 Apple Silicon 上 ONNX 推理的标准优化，transcribe-rs 已实现只是未启用；编译时 feature flag 一行，运行时配置几行）

### 3. Silero VAD params

**当前值**：
- `src-tauri/src/audio_toolkit/silence_gate.rs:22`: `DEFAULT_VAD_THRESHOLD = 0.3`
- `src-tauri/src/audio_toolkit/silence_gate.rs:19`: `DEFAULT_MIN_VOICE_FRAMES = 8` (= 240ms cumulative)
- `src-tauri/src/managers/audio.rs:122`: `SileroVad::new(vad_path, 0.3)` — threshold = 0.3（硬编码）
- `src-tauri/src/managers/audio.rs:124`: `SmoothedVad::new(Box::new(silero), 15, 15, 2)` — prefill=15 frames (450ms), hangover=15 frames (450ms), onset=2 frames (60ms)
- `src-tauri/src/audio_toolkit/vad/silero.rs:9-10`: frame = 30ms @ 16kHz = 480 samples

**分析**：
- threshold=0.3 偏低 → 背景噪音容易触发 speech，导致无声音片段也送进 ASR（hallucination 来源之一）
- hangover=15 frames = 450ms → 尾部静默延迟 450ms 才切断，t3_vad 时延高
- prefill=15 frames = 450ms → 每次录音必须先缓冲 450ms（即使说话已开始），首词可能被截
- onset=2 frames = 60ms → 2 帧连续 voiced 才算开始，防止单帧噪音触发（合理）
- `silence_gate.rs` 的 `min_voice_frames=8` 是 batch-mode pre-filter；audio.rs 的 SmoothedVad 是 streaming filter，两者独立

**候选值**：
1. threshold: 0.3 → 0.5（减误触，Silero v4 推荐范围 0.3-0.7；0.5 是多数用例的 sweet spot）
2. hangover: 15 → 8 frames (240ms)（减尾段等待，代价是句尾可能轻微截词；240ms 对汉语字符间停顿够用）
3. prefill: 15 → 8 frames (240ms)（减首词截断风险，240ms pre-roll 已够 SenseVoice）
4. min_voice_frames (silence_gate): 8 → 6（适当放行短命令）

**预期影响**：
- threshold 升高 → t3_vad 时延不变，但误触发减少，节省 t5 推理（不必跑 SenseVoice 在噪音上）
- hangover 降低 → t3_vad 阶段 p99 尾延减少 ~200ms
- 精度影响：threshold 过高（>0.6）可能截断较弱的说话声（老人/低声），需用真实语音实测

**风险**：
- threshold 0.5 的主要风险：低音量说话（小孩/弱麦）miss 开头，建议先测 0.4 再 0.5
- hangover 降低 + onset 不变 = 更快结束录音，对语速慢或说话中有停顿（思考停顿）用户可能截断句子中间

**ROI**: **中**（延迟改善明显但精度风险需实测，属于"先调 0.4 看 log，再决定 0.5"的逐步实验型优化）

### 5. MLX Qwen3 decoding params

**当前值** (`src-tauri/mlx_bridge_pkg/Sources/MLXAudioBridge/bridge.swift:178-183`, `bridge.swift:288-293`):
```swift
// 两处 (batch + streaming) 相同配置：
let params = STTGenerateParameters(
    maxTokens: 4096,
    temperature: 0.0,    // greedy decode
    verbose: false,
    language: ""         // auto-detect
)
// Model: mlx-community/Qwen3-ASR-0.6B-8bit (int8 量化)
```

**分析**：
- temperature=0.0 (greedy) → 最快、最确定性，无需改；beam search 会 ×2-4 推理时间
- maxTokens=4096：覆盖 ~3000 汉字/30min 语音；Chinese ASR 场景通常 <200 tokens，但设大不影响短句速度（EOS 触发早结束）
- language="" (auto-detect)：对于明知中文用户，可测 language="zh" 跳过 lang detect
- int8 量化：已是预量化模型（mlx-community 的 8bit），内存 ~600MB；int4 候选需要重新量化
- repetition_penalty：未设置（默认=1.0）→ 可能出现尾段重复 token（常见 LLM ASR 问题）

**候选值**：
1. `language: "zh"` 代替 `""` — 如果用户以中文为主，跳过 language detection，推测 first_token_ms -20-50ms
2. repetition_penalty ≈ 1.05-1.1 — 减尾段重复（需确认 `STTGenerateParameters` 是否暴露此参数）
3. int4 量化：内存 ~300MB（-50%），first_token_ms 可能 -10-20%；但精度风险：中文 ITN / 数字 / 专名可能退化，**需跑 regression test**
4. maxTokens 4096 → 1024：中文口语录音用途（<5min 以内）；但长录音会截断，不建议（除非 app 场景明确限短句）

**预期影响**：
- language="zh": first_token_ms 轻微改善（<5%），精度无损
- int4: 内存 -50%，t5 inference 轻微提速；但 ITN/数字精度需验证
- repetition_penalty: 减 hallucination，无速度影响

**风险**：
- language="zh" 对双语用户（中英混）会降英文准确率
- int4 精度损失在数字/时间/专名上最显著（汉字 BPE 压缩 loss 集中在 rare token）；**需先跑 baseline WER 对比**
- `STTGenerateParameters` 是否有 repetition_penalty 参数需先查 mlx-audio-swift API

**ROI**: **中**（language="zh" 是低风险快改；int4 是高收益高风险，归入"留"待 M5 regression baseline 后决定）

### 6. rubato resampler

**当前值** (`src-tauri/src/audio_toolkit/audio/resampler.rs:1-25`):
```rust
use rubato::{FftFixedIn, Resampler};
const RESAMPLER_CHUNK_SIZE: usize = 1024;
// ...
FftFixedIn::<f32>::new(in_hz, out_hz, chunk_in, 1, 1)
// sub_chunks=1, channels=1
```

**分析**：
- 已使用 `FftFixedIn`（FFT-based，非 Sinc-based）✅ — 已是更快的 resampler 类型
- `chunk_in = 1024` samples：@ 48kHz = 21.3ms per chunk；较小 chunk 降低内存但增加 FFT call 频次
- `sub_chunks = 1`：无分片，每 chunk 做一次 FFT
- channels = 1（单声道，正确）
- 无 `SincFixedIn` — 没有"切换到 FFT"的空间，已经是 FFT

**候选值**：
1. `RESAMPLER_CHUNK_SIZE: 1024 → 2048`：减少 FFT call 次数（每次 FFT 开销摊薄），代价是 t4 buffer latency 略增 21ms（单次录音 frame 级别影响可忽略）

**预期影响**：
- chunk 翻倍：t4_resample RTF 估 -10-20%；latency 单次增 21ms（pipeline 级别可忽略）

**风险**：极低。FftFixedIn API 稳定，chunk size 是 tradeoff 不是 bug。

**ROI**: **低**（已使用最快 resampler 类型；chunk size 调优收益小，且 t4_resample 通常不是 p99 瓶颈）

### 7. cpal audio capture

**当前值** (`src-tauri/src/audio_toolkit/audio/recorder.rs:283-334`):
```rust
// 策略：使用设备 native default sample rate，由 FrameResampler 降采到 16kHz
let default_config = device.default_input_config()?;
let target_rate = default_config.sample_rate();  // = 设备默认，macOS 通常 48kHz
// buffer_size 未显式设置 → cpal Default (= OS-defined，通常 512-1024 samples @ 48kHz ≈ 10-21ms)
// channels：设备默认（通常 stereo=2，recorder.rs:252-260 做 stereo→mono 平均）
```

**分析**：
- native rate strategy（不强制 16kHz）避免硬件异常，正确 ✅
- macOS 内建麦克风默认通常 48kHz，内置 USB 麦克风可能 44.1kHz 或 16kHz
- buffer_size = Default = OS 决定（macOS CoreAudio 通常 ~10ms = 480 samples @ 48kHz）
- 如果设备支持 16kHz native，可以跳过 FrameResampler（t4 阶段 = 0）
- stereo→mono：两通道平均，相当于 -3dB SNR 损失；部分设备双声道包含 echo-canceled signal

**候选值**：
1. 检测设备是否支持 16kHz → 若支持则设置 `target_rate = 16kHz`，FrameResampler 检测到 `in_hz == out_hz` 自动 bypass（resampler.rs:38）
2. channels = 1（尝试强制单声道）— 减 stereo→mono 转换 overhead；但部分硬件不支持，需 fallback

**预期影响**：
- 16k native 捕获（设备允许）：t4_resample = 0ms（完全省掉）；t5 无影响
- MacBook 内建麦克风一般不支持 16kHz（HW 原生 48kHz），所以此优化仅对部分 USB/BT 麦克风有效

**风险**：
- 16kHz 强制：不支持的设备会 cpal error → fallback 逻辑需要正确写
- 单声道强制：部分虚拟音频设备报告仅支持 stereo，强制 mono 会失败

**ROI**: **中**（对使用支持 16kHz 设备的用户有效，但需要检测逻辑；内建麦克风用户无收益）

### 8. macOS QoS class

**当前值**：
- ASR worker (`src-tauri/src/actions.rs:800,892`): `tauri::async_runtime::spawn_blocking(...)` — 使用 Tauri 封装的 Tokio blocking thread pool
- VAD worker (`src-tauri/src/managers/audio.rs:87`): `std::thread::spawn(...)` — 普通 OS 线程，无 QoS 设置
- Transcription thread: `transcribe_rs` 内部在调用线程同步执行（`SenseVoiceModel::transcribe_with`），继承 `spawn_blocking` 线程的 QoS

**分析**：
- `tauri::async_runtime::spawn_blocking` → 底层是 `tokio::task::spawn_blocking` → 使用 tokio blocking pool（默认 512 线程上限），线程 QoS 继承自 parent tokio worker → 通常是 `QOS_CLASS_DEFAULT` 或 `QOS_CLASS_USER_INITIATED`
- macOS 调度器将 `QOS_CLASS_USER_INTERACTIVE` 线程优先分配 P-core（性能核），其他 QoS 可能分配 E-core（效率核）
- Apple Silicon M2/M3 P-core 频率 ≈ 2-3× E-core；如果 ASR 推理跑在 E-core，吞吐量损失可达 50%
- 无 `pthread_set_qos_class_self_np` 或 `DISPATCH_QUEUE_PRIORITY_HIGH` 调用 → QoS 未显式设置
- 实际 QoS 取决于 Tauri 启动时的 runtime 配置（无法静态确认，需实测 `qos_class_self()`）

**候选值**：
1. 在 `spawn_blocking` closure 入口处调用 `pthread_set_qos_class_self_np(QOS_CLASS_USER_INTERACTIVE, 0)` (macOS only, unsafe)
2. 使用 `std::thread::Builder::new().spawn(...)` 并在线程内设置 QoS
3. 配置 Tauri async runtime 使用高优先级线程（需查 tauri-plugin 配置）

**实现示例** (Phase 2 参考)：
```rust
#[cfg(target_os = "macos")]
unsafe {
    libc::pthread_set_qos_class_self_np(
        libc::qos_class_t::QOS_CLASS_USER_INTERACTIVE, 0
    );
}
```

**预期影响**：
- 若当前跑在 E-core：t5_inference RTF 改善 30-100%（粗估）
- 若已在 P-core：无收益
- 实测需要 `qos_class_self()` 打 log 确认当前 QoS

**风险**：
- macOS only (`#[cfg(target_os = "macos")]`)，需条件编译
- `libc::pthread_set_qos_class_self_np` 是非标准 POSIX，需要 `libc` crate（已在依赖链中）
- 若 QoS 已经是 user_interactive（Tauri 可能已设），改动无效但也无害

**ROI**: **高**（若推理线程跑在 E-core，这是最大的无损速度提升；改动 5-10 行；首先需要 QoS 观测确认）

- SLA 影响：tokio 1.47+ 有 LIFO slot 优化（spawn_blocking 更快入队），但 1.43 已包含大部分优化

**候选值**：
1. `transcribe-rs` 升至 0.3.11（与 #2 CoreML 一起，单次 `cargo update transcribe-rs`）
2. `tokio` 升至 1.52（单独 `cargo update tokio`，风险低）
3. tauri plugin 批量 patch 升级（低风险，单次 `cargo update`）

**风险**：patch 版本升级通常无 API 破坏；minor 升级（tauri-plugin-*）需查 migration note，tauri 团队版本一般向后兼容

**ROI**: **低**（patch 升级本身不直接提速，更多是 bug fix；CoreML 必须配合 transcribe-rs 最新版才有意义时 ROI 升为"配套高"）

### 10. Tauri bundle config

**当前值** (`src-tauri/tauri.conf.json:39-45`):
```json
"macOS": {
  "hardenedRuntime": true,
  "minimumSystemVersion": "10.15",
  "signingIdentity": "Handy+ Local Dev",
  "entitlements": "Entitlements.plist"
}
```

**Entitlements.plist** (`src-tauri/Entitlements.plist`):
```xml
com.apple.security.device.microphone           = true
com.apple.security.device.audio-input          = true
com.apple.security.cs.allow-jit               = true   <!-- MLX Metal JIT -->
com.apple.security.cs.allow-unsigned-executable-memory = true  <!-- legacy MLX -->
com.apple.security.cs.disable-library-validation = true  <!-- mlx-audio dylibs -->
```

**分析**：
1. **minimumSystemVersion = "10.15"**：虚标版本号。app 实际需要 macOS 13+（MLX 需要 Metal 3，Apple Silicon = macOS 11+；mlx-audio-swift 用 async/await = macOS 12+；实际 MLX inference = macOS 13+）。低版本声明让 macOS 对 binary 做更多向后兼容检查，轻微影响 startup
2. **signingIdentity = "Handy+ Local Dev"**：残留旧 identity（M4 未完成前 ok，但 FD-003 M4 要换为 "v2t Local Dev"）
3. **`cs.allow-unsigned-executable-memory`**：MLX 新版（macOS 11+）已改用 `allow-jit`，旧 entitlement 可能不再必要但保留为 belt-and-suspenders
4. **entitlement 数量**：5 个，全部有合理理由；无冗余 entitlement（如 `network.client` / `files-readonly` / `get-task-allow` 均未出现）

**候选值**：
1. `minimumSystemVersion: "10.15" → "13.0"` — 准确反映 Apple Silicon MLX 实际需求；macOS 13+ 下系统对 binary 的向后兼容垫片减少，startup 轻微提速；同时移除对 macOS 10.15-12 用户的误导
2. `signingIdentity: "Handy+ Local Dev" → "v2t Local Dev"` — FD-003 M4 遗留项，应在 M4 中修复
3. `cs.allow-unsigned-executable-memory` 评估是否可移除 — 需用 `codesign -dv` 验证 MLX 在仅有 `allow-jit` 时能否正常运行（MLX ≥0.22 推荐 allow-jit alone）

**预期影响**：
- minimumSystemVersion 升级：startup_ms 可能 -10-50ms（系统少做 compat 检查）；主要价值是语义正确
- signingIdentity 修复：FD-003 M4 阻塞项，与性能无关
- entitlement 精简：sandbox check overhead 微减，难量化

**风险**：
- minimumSystemVersion 升高后，macOS 10.15-12 用户无法运行（v2t = Apple Silicon only，实际不是问题）
- 移除 `allow-unsigned-executable-memory` 前必须在目标系统测试 MLX（否则 SIGKILL）

**ROI**: **中**（minimumSystemVersion 修正有性能+语义双重价值；signingIdentity 是 M4 配套项；低风险）
